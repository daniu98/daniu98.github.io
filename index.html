01About

Real conditions

I like problems where the answer has to survive contact with something other than a test set. A UAV model that has to make the call in three milliseconds. An API that has to make sense of prerequisite text written by 141 different majors, none of them to a spec. A robot that has to find its own way out of a maze with nothing but two IR sensors and whatever I wrote the night before.

The interesting part is almost never the algorithm. Depth-first search through a maze is a classroom exercise; what took months was the custom PCB, soldered by hand through several revisions, before the IR readings were steady enough to act on. The UAV controller needed 9,920 epochs of tuning to hold 27 cm of mean error — and its 3.04 ms inference time counted for just as much, because on an edge device an answer that arrives late is a wrong one.

Right now that looks like document transfer and storage on AWS at Bumblebee Networks, moving diagnostic logs and support-ticket data between branch devices and the cloud, plus the monitoring, failover and threat-detection work that keeps those branches reachable with nobody on site. Before that, two years at Purdue on models small enough to run on the edge, and leading nine engineers on TreeReq, where being clear mattered more than being clever. The work I keep coming back to is infrastructure: the layer other people's work sits on, where a bad decision stays quiet for a long time and then isn't.

Right too late is still wrong.

Proj_012026

Course Prerequisite API & Data Pipeline

TreeReq — Project Lead, Backend & AI

UCLA publishes prerequisites as prose, and 141 departments each write it their own way. A student who wants to know what a course unlocks has to read the catalogue and hold the graph in their head.

I architected a RESTful API on FastAPI and MongoDB that serves course and prerequisite data to a React frontend, and built the pipeline that feeds it: Playwright and Chromium walk the catalogue, and the Claude API turns the prerequisite sentences into structured JSON the API can actually traverse. Nine engineers worked on the platform around it.

Proj_022025 — 2026

Autonomous Maze-Solving Robot

UCLA IEEE — Software Engineer

Put a robot in a maze it has never seen, give it no map and no human input, and have it find the exit. All it knows is what two IR sensors can see from where it is standing.

Depth-first search over a graph the robot builds as it drives: sense the open walls, commit to an unvisited branch, and unwind the stack when the branch dies. The hard part was below the algorithm — I designed and soldered the custom PCB for motor control and sensor integration, through several hardware revisions before the readings were stable enough to trust.

Proj_03Sept — Dec 2025

Autonomous Rover

Personal project

I wanted to understand sensor fusion by building something that fails visibly when you get it wrong: a rover that has to pathfind and dodge obstacles in real time, where a bad heading estimate drives it into a wall.

An Arduino and Java navigation system that fuses gyroscope and distance-sensor input in a closed sensor-motor feedback loop. The chassis is a custom Fusion 360 design, laid out around where the sensors needed to sit rather than the other way round.

Proj_04Sept — Dec 2025

MNIST Digit Classification

Personal project

Everyone’s first CNN hits 98% on MNIST. I wanted to know where the tradeoff between accuracy, training time and overfitting actually lands, which means building more than one of them.

A convolutional network in PyTorch reaching 98%+ accuracy, then several variants with different convolutional and pooling depths to see what each one buys. The panel on the left runs three real convolution kernels over whatever you draw — the same edge and blur responses a first conv layer learns. The trained model itself lives in the notebook.
